# Deepfake Repository Mining: Stated vs. Enacted Ethics and Gender

Replication package for our seminar paper (TU Darmstadt, WS 2026/27).

We mine 30 open-source deepfake repositories on GitHub (face-swap, talking-head/lip-sync, voice cloning and others) to examine how they state AI-ethics values, whether those values become technical safeguards, and whether the gendered harm of deepfakes is acknowledged. The study builds on Pawelec (2025), *"Decent deepfakes?"*, AI and Ethics, which interviewed professional deepfake developers but excluded open-source projects.

## Research questions

- **RQ1 – Stated values:** Which AI-ethics values do open-source deepfake repositories state, how are they framed, and when did the statements first appear?
- **RQ2 – Enacted values:** Are stated values implemented as technical safeguards (NSFW filter, watermark, consent check, detection, usage restriction), and are they on by default?
- **RQ3 – Gender:** Do repositories acknowledge the gendered/sexual harm of deepfakes or document gender and demographic properties of their data and models? How does gender surface in issues and discussions?

## Method in short

1. **Search:** GitHub Search API queries (e.g. `deepfake`, `face swap`, `voice cloning`, `lip sync`, topic tags), restricted to ≥ 100 stars.
2. **Selection:** automatic and manual exclusion (forks, lists, detection-only tools, datasets, wrappers), then a stratified sample of 30 repositories by tool type. The count after each step is logged.
3. **Collection:** partial clones (text files and history only, no model weights), plus metadata, issues and pull requests via the API.
4. **Extraction:** keyword dictionaries and `git grep` / `git log` produce **candidate** evidence with file, line, context and permalink.
5. **Manual coding:** two coders verify the candidates against a codebook. An overlap subset is coded by both, and Cohen's κ is reported.
6. **Analysis:** counts per value and tool type, stated-vs-enacted cross-tabs, timelines and gender categories. Tables and figures are exported for LaTeX.

> Keyword hits are candidates only. All reported results are based on manually verified codes.

## Repository structure

```
mining/            pipeline code (one module per stage)
  config.yaml      queries, thresholds, keyword lists, seeds, events
  codebook.py      codes, definitions, keyword dictionaries
tests/             unit tests
data/              mined data (not committed, regenerated by the pipeline)
output/
  s1_candidates.csv, s2_flow.csv, s2_excluded.csv, s2_sample.csv
  evidence/        per-repository evidence files with links
  coding/          coder sheets, codebook, agreement, final codes
  tables/ figures/ latex/   paper-ready outputs (incl. numbers.tex)
  REPORT.md        summary of all results
```

## Setup

Requirements: Python 3.11+, git, and the [GitHub CLI](https://cli.github.com/).

```bash
git clone https://github.com/<user>/<repo>.git
cd <repo>
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
gh auth login                      # provides the API token
```

Alternatively, set a token manually: `export GITHUB_TOKEN=...` (never commit it).

## Usage

Run the full pipeline:

```bash
python -m mining run-all
```

Or run single stages:

```bash
python -m mining search      # S1 sampling frame
python -m mining select      # S2 inclusion/exclusion + stratified sample
python -m mining collect     # S3 clone + metadata + issues
python -m mining extract     # S4 candidate evidence
python -m mining sheets      # S5 coding sheets
python -m mining agreement   # S6 Cohen's kappa (after manual coding)
python -m mining analyze     # S7 tables + figures
python -m mining report      # S8 REPORT.md
```

Options: `--refresh` ignores the cache, and `--repo owner/name` runs a stage for one repository.

API responses are cached, so re-runs do not use extra API quota.

## Manual coding workflow

1. Review repositories flagged `needs_manual_check` in `output/s2_sample.csv`. Adjust `manual_overrides` in `config.yaml` and re-run `select` if needed.
2. Coder A fills `output/coding/coder_A.xlsx` and Coder B fills `output/coding/coder_B.xlsx`. Each coder edits **only** their own file.
3. Run `python -m mining agreement`, then discuss the disagreements in `output/coding/disagreements.csv` and fill the `resolved` column.
4. Run `python -m mining analyze` and `python -m mining report`.

Until manual coding is complete, all outputs are marked **PRELIMINARY**.

## Using the results in the paper

Copy `output/latex/` into the LaTeX project and add:

```latex
\input{numbers.tex}   % \newcommand macros for every reported number
\input{tables/...}    % booktabs tables
```

This keeps every number in the text consistent with the data.

## Ethics and data protection

- No code from mined repositories is executed, installed or imported. Files are only read as text.
- No model weights, datasets or media are downloaded (`GIT_LFS_SKIP_SMUDGE=1`, files > 2 MB skipped).
- Commit author e-mails and names are not stored. Issue and PR authors are pseudonymised (`user_<hash>`).
- Quotes are kept short and used only to illustrate findings.
- Findings describe what repositories **state and implement**, not what individual developers believe.

## Limitations

The sample is small (30) and English-only, with GitHub stars as a popularity proxy. All data comes from a single snapshot date, and keyword-based candidate search can miss evidence that the dictionaries do not cover. See the Threats to Validity section in the paper and `output/REPORT.md`.
